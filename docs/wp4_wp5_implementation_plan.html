2 · The three exposure builds (WP5)

A nested ladder — each build adds exactly one refinement, so any change in calibration or net benefit is attributable to that single step. All weighting is done in an equal-area CRS (SLD99 / Sri Lanka Grid or UTM 44N) — never in WGS84 degrees. Every build is row-aligned to the same 10,842 unit-week keys so they diff cleanly, and each is checksummed + frozen.

A · Area-mean
EXISTS — Build A
  • Naive areal mean (all_touched mask).
  • 417 ISO weeks × 26 RDHS = 10,842 rows.
  • The current baseline every downstream result consumes.
B · Population-weighted
TO BUILD — Build B
  • Weight each climate cell by WorldPop population in it (fractional-cell overlap, not all_touched).
  • Population vintage matched to the exposure year.
  • Carries within-unit dispersion (SD, IQR) as a WP6 covariate.
C · Terrain-corrected
TO BUILD — Build C
  • Lapse-rate correct temperature to a DEM (Copernicus GLO-30, −6.5 °C/km) at the fine grid before aggregation.
  • Aggregated with the same population weighting as B → isolates the terrain effect.
  • Differs from B on temperature only; precip/RH carried through unchanged.
A  →  +population weighting  →  B  →  +altitude correction  →  C
In plain language Each district is a big chunk of land, but the model needs one temperature and rainfall number per district per week. How you squash the whole district into one number is a choice. A just takes a plain average of the whole area. B leans the average toward the spots where people actually live (a highland district's people may sit in a warm valley, not on the cold peaks). C goes further and corrects temperature for altitude before averaging (air gets colder as you go up). We build all three and check whether that choice alone changes who gets a dengue warning.
Why Build C earns its place. Elevation is the top-ranked geospatial modifier in the 2026-07-02 literature review, and in Sri Lanka's central highlands (Nuwara Eliya, Kandy, Badulla) altitude correction plausibly moves temperature more than population-weighting does. That makes it the difference between "we weighted by people" and a genuine terrain-vs-population MAUP story.

The variable set carried through all three builds is not just temperature/rain/humidity — the screening in §5 adds three more free, already-in-hand weather variables: DTR, absolute humidity/VPD, and a drought index (SPI/SPEI). Builds (how you average) and variables (what you average) are separate axes.

3 · Two-country cross-validation (WP4)

"Spatial cross-validation" stops a held-out area's near neighbors — which share weather and outbreak timing — from leaking the answer through the training set. The two settings are so different in size that they get different, size-matched schemes. In both, temporal honesty is preserved inside every fold (lags built from the past only) → spatio-temporal CV.

In plain language To prove the model works in places it hasn't seen, we train it on some districts and test it on others it never saw. The catch: next-door districts have almost the same weather and outbreaks, so if a district's neighbor is in the training set the test isn't really "new" — the answer leaks in. So when we test one area, we also hold back its immediate neighbors from training. Sri Lanka has only 26 districts (test them one at a time), Colombia has ~1,000 (test a whole region at a time) — same idea, sized to each country.

🇱🇰 Sri Lanka — buffered LOOCV

26 RDHS · too few for blocks

  • Hold out one district as the test unit; train on the other 25.
  • Buffer: also drop the held-out district's within-range neighbors from training.
  • 26 folds; record buffer size & train/test counts per fold.
  • Emit fold/buffer definition as a versioned artifact.
Power caveat: at n=26 each test fold is a single district and the buffer shrinks it further — report as a sensitivity companion, not the headline test. Flag to PI (SOW §N).

🇨🇴 Colombia — spatial block CV

~1,000 municipalities · well-powered

  • Group municipalities into contiguous blocks ≥ the autocorrelation range — or leave one whole department out (interpretable default).
  • Buffer strip so train/test units are never within range.
  • Balance folds on outbreak prevalence & unit-week count.
  • Emit fold-definition files (unit → fold id).
Carries the claim: Colombia's size makes this the well-powered external-validation test the paper leans on.
Shared step first: fit the reference model, extract residuals, and estimate the residual spatial autocorrelation range (empirical variogram / Moran's I decay) separately per country. That range sets the buffer width (SL) and the minimum block size (Colombia). Then a leakage-audit memo confirms zero train/test neighbor pairs fall within range.

4 · The four extras — in plain language (D4)

The core of the paper is Sections 2 + 3 (the three builds and the two-country test). These four "extras" all exist to strengthen or defend that core — none of them is a new model. They were all accepted for this paper (decision D4).

First, the shared idea — MAUP Three of the four are about MAUP (the "Modifiable Areal Unit Problem"). That's just the fact that your answer can change depending on how you draw and average over areas. Since a district gets squashed into one weather number, the way you do that squashing is a choice — and MAUP is the worry that a result is really about that choice, not about dengue. These extras poke at that worry from different angles.
1.Per-variable MAUP cost: cheap
What it is: report the averaging effect separately for each weather type (temperature vs rainfall vs humidity), instead of pooling them into one number.
Why (plain): rain is patchy — a storm soaks one town and skips the next — so how you average it over a district matters a lot. Temperature is smooth — it barely changes across a district. So the averaging choice should matter a lot for rain and hardly at all for temperature. Showing this tells reviewers which weather inputs are fragile.
Work: almost free — it's a breakdown of a number we already compute.
2.Map of where forecasts go wrong — Figure F8 cost: moderate
What it is: the model can be miscalibrated — it says "20% chance of outbreak" where outbreaks actually happen 40% of the time. This checks whether those errors cluster in certain kinds of place (dense cities, high altitude, greener land, near water) and maps where warnings would flip.
Why (plain): it turns an abstract statistic ("the model is off") into an actionable map — "the model is worst in dense, low-lying areas near water." That's the bridge to the WP6 decision-flip map.
Guardrail: geography is used to explain the errors, never added as a new predictor to boost accuracy (the "no new model" rule).
3.Cross-setting MAUP (do it in Colombia too) cost: moderate
What it is: run the same weather-averaging comparison in Colombia, not just Sri Lanka.
Why (plain): if the averaging choice changes decisions in both a small compact country and a big varied one, the finding generalizes and is much harder to wave away. Colombia is more varied (Andes, coast, Amazon), so it may matter even more there.
Work: Colombia's pipeline already exists — this re-runs it under the three builds.
4.Different population maps lowest priority · trim first
What it is: Build B leans the weather average toward where people live — using a "population map." There are several (WorldPop, GHSL, census). This swaps them and checks whether the answer moves.
Why (plain): a "check on the check" — it makes sure Build B's result isn't an artifact of one particular population dataset. If all three agree, the finding is robust.
Priority: a second-order robustness check — the first thing to cut if the timeline gets tight.

Deliverables checklist

  • Tables: Build B …_v2_popweighted.csv, Build C …_v3_terraincorrected.csv, population-product variants — each with the 3 new variable columns (DTR, abs-humidity/VPD, SPI/SPEI).
  • F8 covariate table: one static row per district (built-up, elevation, NDVI, distance-to-water, healthcare access, wealth index, + optionals).
  • Figures: F2 exposure contrast (SL + Colombia) · F7 net-benefit sensitivity · F8 decision-flip / miscalibration map.
  • CV artifacts: SL buffered-LOOCV folds · Colombia block-CV folds · leakage-audit memo.
  • Writing: Methods subsections for WP4 (two-country CV) and WP5 (three-build MAUP + factor screening).

5 · Factor screening — what's in, what's out, and why

The literature review (dengue_geospatial_risk_factors_review.html) catalogued 23 geospatial dengue risk factors. Below, every one is screened against four hard tests. The plan follows an include-then-prune rule: bring in each factor that clears all four tests, then drop it later if it carries no signal in the results.

The four screening tests (a factor must pass all four to be included)

1 · Free & open dataThe source must be freely and practically downloadable. Survey micro-data, gated feeds, and paid imagery fail this test — and are dropped with the access reason stated.
2 · Right resolutionDerivable at district × epi-week (for the exposure layer) or as one static value per district (for the F8 miscalibration map).
3 · Allowed roleEnters only as (A) exposure construction or (B) an F8 miscalibration explainer — never a new accuracy predictor (no-new-model rule).
4 · Evidence worth itEvidence ≥ moderate, or so cheap (a transform of data we already hold) that testing it costs almost nothing.

5.2 · Step-by-step recipes — the 3 new exposure variables

Each is computed on the fine grid, then aggregated to district under each build (A area-mean · B population-weighted · C same as B) and appended as new columns, row-aligned to the existing exposure tables.

DTR — diurnal temperature range
Source: ERA5-Land 2 m temperature (Copernicus CDS) — already acquired · free
  1. Per grid cell per day, take daily Tmax and Tmin from the hourly/daily ERA5-Land temperature.
  2. Compute DTR = Tmax − Tmin for each cell-day.
  3. Average cell-day DTR to the ISO-week.
  4. Zonal-aggregate to each district under builds A / B / C.
  5. Append dtr_mean (+ within-unit SD) to each exposure table.
Absolute humidity / vapour-pressure deficit (VPD)
Source: ERA5-Land 2 m temperature + 2 m dewpoint (Copernicus CDS) — already acquired · free
  1. Per cell, get 2 m temperature t2m and dewpoint d2m.
  2. Saturation vapour pressure es(T) via August–Roche–Magnus; actual vapour pressure ea = es(d2m).
  3. VPD = es(t2m) − ea; absolute humidity from ea via the ideal-gas relation.
  4. Weekly mean → zonal to district under A / B / C.
  5. Append vpd_mean and abs_humidity_mean.
Drought index — SPI (and SPEI)
Source: CHIRPS rainfall (UCSB) — already acquired; PET for SPEI from ERA5-Land temperature (Hargreaves) · free
  1. Build a district monthly rainfall series from CHIRPS (SPI); for SPEI, form precip − PET.
  2. Fit the standardized index against the full climatological baseline at 1-, 3-, and 6-month scales.
  3. Map each month's index onto its ISO-weeks (carry-forward or interpolate).
  4. Append spi_1 / spi_3 / spi_6 (and SPEI) as lagged drought features.

5.3 · Step-by-step recipe — the F8 map covariate panel

One static value per district for the miscalibration map
Recommended environment: Google Earth Engine (free for research) — hosts GLO-30, ESA WorldCover, GHSL, MODIS, VIIRS, JRC Surface Water in one place, so no bulk downloads. Direct-download fallbacks exist for every layer.
  1. Load the district polygons (26 RDHS / Colombian municipalities).
  2. For each covariate, reduce its source raster over each polygon: mean (NDVI, built-up %, nightlights, wealth), fraction (urban cover), or min-distance (surface water, health facility).
  3. Export one row per district → join to the per-district calibration results.
  4. Regress per-district calibration slope/intercept and ΔNB on the panel; keep covariates that carry signal, drop the flat ones.
  5. Render the surviving covariates as the F8 decision-flip / miscalibration map.
Honest handling (pre-registered) — mandatory with a large panel. Because we deliberately keep a broad optional covariate set, this discipline is not optional: pre-specify every covariate up front, treat the panel as exploratory-explanatory, control the false-discovery rate (report all covariates tried, not just the significant ones), and never re-import a "significant" covariate as an accuracy predictor. Dropping a flat covariate is the expected, clean outcome — not a failed analysis. The bigger the panel, the stricter the multiplicity control.

6 · Do the geomatics factors actually help predict? (the stress test)

Section 5 picked a good set of geomatics factors. This section puts them to the test: do they actually help decide when to warn a district — and if so, which ones? We answer that honestly, without turning the paper into a "we built a new predictor" study.

The idea in one line Build a model from the geomatics factors, keep only the ones that genuinely earn their place, then check whether adding those to the recent-cases model helps real warning decisions. If they don't help, that's a strong result too — it confirms recent case counts are hard to beat.

The approach — three simple steps

Build broad
STEP 1
  • Make a model that uses geomatics factors only.
  • Include the ones that change week to week (temperature, rain, humidity, drought, surface-water extent, greenness) and the fixed ones (elevation, built-up, wealth, distance to water).
  • The changing factors give it a shot at timing; the fixed ones set each place's baseline risk.
Keep only what matters
STEP 2
  • Test many times over different districts and keep the factors that keep proving useful — ignore one-off flukes.
  • Produce the "which factor matters most" ranking you asked for.
  • Keep "matters for which place" separate from "matters for which week" — they'll have different winners.
Fold winners into a hybrid
STEP 3
  • Take only the useful factors and add them to the recent-cases model (a hybrid / ensemble).
  • Judge it with the same fair yardsticks as every other model (calibration + net benefit).
  • Ask: does adding geomatics change any real warning decisions?
build broad  →  keep what matters  →  test the hybrid on real decisions
Two rules that keep it honest.
  • No cheating (no leakage): pick the factors on one set of districts and test them on different ones — we reuse the leakage-proof spatial folds from §3. Skip this and both the "important" factors and the score come out falsely good — the #1 thing reviewers attack.
  • Don't trust a single winner: factors that move together (elevation, temperature, urbanisation, wealth) swap ranks run to run. Keep the ones chosen consistently across folds and show the uncertainty — never a lone "best factor".
Why this is worth including.
  • If geomatics doesn't help → it powerfully confirms the paper's headline (recent cases win) and is reviewer-proof: "we gave geomatics every chance and it still didn't beat recent cases."
  • If geomatics does help → a genuine new finding, and the seed of a follow-up paper.
  • Either way, it gives an honest answer to "which geomatics factor matters most" — the question you asked.
  • It stays inside the "no new model" promise because it's framed as a test / evaluation, not a proposed new warning system.
Scope & sign-off. This adds a model, so it needs a heads-up and sign-off from the PI. Building a full new geomatics predictor as the paper's centerpiece is a different, bigger study — that version is Paper 2. Here it stays a bounded, pre-specified stress test with the honest-null clause in force.

8 · Guardrails & honest-null

  • No data committed — code + reports only. New tables and fold definitions are checksummed + FREEZE_LOG'd before any result is quoted; never committed.
  • No-new-model rule — geospatial modifiers stay explanatory (why calibration varies in space); they are never added as new accuracy predictors.
  • Equal-area CRS invariant — all weighting in projected coordinates; validate zonal means against station data where available.
  • Honest-null clause (SOW §N) — if weighting / terrain correction moves neither exposure nor net benefit, report it as a clean null. "Exposure construction does not change the decision" is itself a publishable, reviewer-disarming result — do not manufacture a finding.
